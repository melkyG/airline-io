So from the user’s perspective, bulk unassign already behaves correctly, and we don’t gain much by adding a separate atomic bulk-unassign endpoint right now.

The main limitation is atomicity: if one request in the middle of a multi-unassign batch fails, earlier ones may already have succeeded. If that becomes a real gameplay problem later, we can add a true server-side bulk endpoint then.
